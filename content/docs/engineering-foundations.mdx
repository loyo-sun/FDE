## 适用场景与学习目标

面向能阅读基础代码、但尚未独立完成客户项目的工程师。目标是把“本机能跑”推进到“别人能复现、异常能定位、变更能撤回”。先选择一种团队熟悉的语言，不需要同时学习所有框架。

## 建立最小工程闭环

1. 建立版本仓库，提交依赖锁文件、配置样例和启动说明；真实凭据不进入仓库。
2. 实现一个读取合成工单的服务，提供健康检查、详情查询和错误响应。
3. 在请求入口校验参数，在业务层检查状态，在存储层维护唯一约束。
4. 为正常查询、未知编号、无权限和依赖超时各写一个验证用例。
5. 从干净环境按说明安装、启动和执行验证；由另一位同学复现。

## 应掌握的基础与验证方式

| 基础 | 项目中的用途 | 掌握证据 |
| --- | --- | --- |
| HTTP、DNS、TLS | 分清连不上、身份失败和业务失败 | 解释一次失败请求经过的层次 |
| SQL、事务与索引 | 维护状态和避免重复写入 | 用重复请求验证业务唯一性 |
| Git 与代码审查 | 追踪改动并恢复版本 | 从提交定位变化，提交可读差异 |
| 进程、资源与日志 | 识别退出、阻塞和资源不足 | 用追踪编号找到错误环节 |
| 测试与依赖管理 | 控制升级引入的变化 | 锁定版本并在干净环境复现 |

## 贯穿案例：先做查询，再做 AI

售后工单助手首先应该能够读取工单 T-101、显示状态、所属租户和设备型号。返回不存在的编号时使用明确错误；用户请求其他租户的工单时返回不泄露内容的结果。只有这条确定性链路验证通过，才增加文档检索和回复草稿。

网络诊断按“名称解析 → 连接 → TLS → HTTP → 业务响应”排查。不要看到超时就增加重试；先查明调用是否已被对方执行，否则可能重复创建工单。

## 常见失败与改进

- 只保存截图：同时保存脱敏请求、响应和版本，才能复现。
- 开发和生产配置混在一起：显式区分环境，并在启动时拒绝缺失配置。
- 一次提交全部修改：按可解释的业务行为拆分，并记录验证结果。
- 用真实客户数据练习：本知识库只使用合成数据，接入真实环境另行确认用途与权限。

## 练习与完成标准

提交最小服务、配置样例、四类用例和运行说明。随机换一台环境后能复现；失败响应包含稳定错误码和追踪编号，日志没有凭据或工单敏感正文。下一步阅读[客户访谈](/docs/business-discovery/)与[工程质量](/docs/engineering-quality/)。
